# OCR 总体选型结论

更新2026-10-30，第三轮已纠正评分并实跑四方案各120项；旧两轮覆盖率保留历史意义，不再作为整体识字排名

## 当前判断

**Mac快速提字先试Apple Vision，跨平台/文字坐标用RapidOCR；整页转Markdown保留MinerU Basic，多格式结构接入保留Docling。暂时没有整页准确率冠军**

新一轮的60个文字区域（40中文/混排、20英文，共2322个非空白字素）得到：

| 方案 | 中混区域CER | 英文区域CER | 原60整图平均秒/张 |
|---|---:|---:|---:|
| RapidOCR | 13.43% | 3.34% | 1.132 |
| Apple Vision | 14.47% | 1.97% | 0.419 |
| MinerU Basic | 14.21% | 18.49% | 2.503 |
| Docling + RapidOCR | 17.16% | 10.87% | 2.089 |

错误率与整图速度来自两套不同输入，不能合并解释成整页精度速度排名。中混组误差区间很宽且重叠；只有685个汉字，纯汉字辅助CER分别8.32%、14.60%、5.40%、10.07%，忽略非汉字错误，不能替代主指标。MinerU区域空输出7/60、Apple竖排繁体区域全漏，说明输入形态决定适用性

Rapid观察峰值15.59GiB出现在极窄竖排区域，不能再笼统承诺低内存；Apple0.33GiB、MinerU4.41GiB、Docling7.84GiB。均为采样进程树RSS之和，非系统净物理内存

[完整新报告](../data/reports/benchmark-v3.md)记录S/D/I、空输出、时间、峰值及区间；[评价协议](ocr-evaluation-v3.md)解释参考复核、正文提取和不能外推的范围

## 前两轮工程起点（历史记录）

默认采用两条路线：图片提取文字和坐标用RapidOCR；中文文档转Markdown/JSON用MinerU Basic。需要多格式统一文档接口时选Docling。没有必要同时集成九套方案

| 要完成的工作 | 当时选择 | 依据与边界 |
| --- | --- | --- |
| 截图识字、界面自动化、文字坐标 | RapidOCR默认；PaddleOCR作专项对照 | 历史游戏截图曾实际采用RapidOCR；新60份Rapid约71秒，街景答案6/6命中。新样本没有系统覆盖GUI，不能宣称全部截图最准确 |
| 只面向Mac的快速提字 | Apple Vision备选 | 60份约33秒，中文表单覆盖73.6%；英文表单较弱。是否替代Rapid须用真实应用截图验证 |
| 中文文档、扫描页转Markdown/JSON | MinerU Basic优先试用 | 中文表单覆盖86.8%，60份约123秒，无报错/截断；结构、公式准确率尚未验证 |
| 多格式文档接入、统一结构供检索/后续处理 | Docling备选 | 本地60份完成，中文表单75.9%、英文58.8%，约104秒；使用RapidOCR后端，不能算完全独立的识字模型 |
| 已裁剪的单行文字 | RapidOCR仅识别模式或PaddleOCR | Rapid追加诊断CER从58.8%降至8.8%，证明输入形态与调用方式很重要；仅6张34字，且为事后诊断 |
| 扫描PDF保持原貌并添加搜索层 | OCRmyPDF功能候选 | 只有调研，未实测，不承诺本机效果；它解决的目标不同于Markdown转换 |
| 复杂旧扫描、手写、表格/公式精确还原、票据字段 | 尚未定型 | 当前证据不足，不以普通文本覆盖率替代这些能力的准确率 |

这里的默认是工程起点，不是全场景准确率冠军；真实业务上线前只需对选定路线补业务样本验证

## 前两轮九方案去留（历史记录）

两轮共9条方案，各60份主测，Tesseract另重复60份补测内存；不是9个独立模型家族。第二轮与第一轮同输入、同评分，设备与内存测量方式不同

| 方案 | 当时决策 | 理由 |
| --- | --- | --- |
| RapidOCR | 日常识字默认 | 历史业务已用，速度与接入便利；默认检测不适合所有裁剪行 |
| PaddleOCR / PP-OCR | 保留对照，按场景启用 | 首轮中文表单优于Rapid；当前固定CPU配置约542秒，未证明适合全部任务 |
| Apple Vision | Mac快速备选 | 速度快，中文有竞争力；不跨平台，英文/旧扫描未胜出 |
| MinerU Basic | 中文文档主候选 | 当前中文表单覆盖最高，速度可接受；不是通用截图引擎 |
| Docling | 文档接入备选 | 多格式和统一结构路线；结构输出存在不等于结构正确 |
| GLM-OCR / MLX | 实验候选，不作默认 | 英文表单67.6%、混合文档47.4%为已测较高值；3/60截断，约793秒 |
| PaddleOCR-VL / MLX | 暂不纳入默认流程 | 6/60截断，约405秒；只测整图调用，未测官方布局切块流水线 |
| Tesseract | 保留兼容/工具链用途 | 当前多语言配置中文、街景较弱；不能外推英文专项能力。含子进程RSS补测约0.26GiB |
| EasyOCR | 当前不优先 | 本次质量没有优势，约200秒，首轮RSS约17.63GiB |

## 只调研、没有实测的范围

- 文档工具：OCRmyPDF、PP-StructureV3、Marker/Surya
- 视觉模型：HunyuanOCR、DeepSeek-OCR 2、dots.ocr/dots.mocr、olmOCR；注意使用olmOCR-bench样本不等于测试了olmOCR模型
- 云服务：Mistral OCR、Google Document AI、Azure Document Intelligence、腾讯云OCR、百度OCR、Amazon Textract
- MinerU高档位，以及GLM/PaddleOCR-VL的官方完整布局流水线，也没有测

这些候选来自已有Exa官方资料调研，当前只整理历史记录，没有重新联网核验版本/价格/许可。未测不代表效果差，也没有证据让它们替换已测方案

## 前两轮错误率的边界

前两轮不能给可信的整体错字率。表单和文档使用严格片段覆盖率，不能用100%减覆盖率算错字率；参考数据存在已发现标注错误。结构/公式没有人工金标准

前两轮只有6张招牌行共34字有CER：GLM5.9%，PaddleOCR及PaddleOCR-VL8.8%，Rapid默认58.8%但事后仅识别诊断8.8%，MinerU47.1%，Vision50.0%，Docling55.9%，EasyOCR67.6%，Tesseract100%。这组数字只解释该小样本，不能拿来排整体准确率

生成截断率是另一件事：GLM5%，PaddleOCR-VL10%；其他方案未出现此类截断，但仍可能漏字、空输出或错误识别

## 后续真正有价值的验证

当前文字区域CER已重测，别再靠扩模型名单解决评价问题。若要决定整页文档主方案，需额外建立完整且阅读顺序明确的整页GT，最好独立双人校验，再评价文字与表格/公式结构。这不是当前已完成的部分

## 格式偏差复核（历史问题，v3已修正）

正式表单/文档成绩采用参考片段覆盖，不是整页CER：在“## 春天”中仍能命中参考“春天”，标题前缀不会直接降低该项覆盖。中文表单MinerU86.8%的原结论在原口径下仍成立，但多字/幻觉不被充分惩罚，格式插入片段内部也可能影响命中，不能推出整体准确率最高

旧版正式ReCTS小样本CER与Gradio输出CER都存在格式偏差。只读诊断中，MinerU六张34字剥离标题前缀和空图片占位后，编辑数由16降至13，CER由47.1%降至38.2%；这不是所有引擎按统一纯文本规则重评的结果，原报告未覆盖。v3已统一提取正文、保留原始输出，重跑并另存结果；网页也改为同一正文CER。文字质量与结构质量分开
