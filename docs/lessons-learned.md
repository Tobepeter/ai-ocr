# OCR选型与评测经验

2026-10-30 · 来自本项目实际调研、三轮测试和代码审查；候选介绍不等于本机实测结论

## 选型先看输出目标

Mac快速提字先试Apple Vision；跨平台图片文字与坐标用RapidOCR；整页文档转Markdown保留MinerU Basic；多格式结构接入保留Docling。Docling使用RapidOCR后端，不是完全独立的一种识字模型

这是工程起点，不是全场景准确率榜。完整结果见[总体选型](ocr-selection.md)与[第三轮报告](../data/reports/benchmark-v3.md)。只有文字区域有统一参考CER，尚无可靠整页冠军

## 最容易得到假结论的地方

| 经验 | 本项目证据 | 后续做法 |
|---|---|---|
| 覆盖率不是正确率 | 指定片段出现就算命中，重复/补字未充分扣分 | 文字质量用顺序编辑距离，保留S/D/I；不计算1减覆盖率 |
| Markdown不能直接和纯文本比 | 标题符号、图片编码产生伪插入 | 从结构化文字节点提取；生成格式不计，真实编号/符号保留 |
| 原始标注也会错 | 大小写、标点、复选框、裁剪边缘出现问题 | 看模型输出前核对并冻结；保存原标注、修正理由与SHA256 |
| 裁剪会改变流水线行为 | MinerU部分小区域空输出，Rapid极窄竖排触发高内存 | 区域识字与整页解析分测；不把rec-only诊断混入默认流水线排名 |
| 语言/领域分组影响结论 | 40中文混排来源不等于所有字符都是汉字；竖排与手写难例影响总值 | 分来源/语言展示，记录分母；纯汉字等辅助指标明确忽略了什么 |
| 空输出不是成功识别 | 进程退出0也可能没有文字 | 退出码、空输出率、错误率分别报告，失败不能从准确率分母中删掉 |
| 评分器失败不等于OCR失败 | 评分异常曾将正确OCR算成100%错误 | 识别/评分状态独立，评分不可用保留原始结果 |
| 没跑的样本不是0秒 | 缺失文件曾降低平均耗时 | 时间用null，成功延时与失败耗时分开，中止批次不排名 |

## 运行与复现经验

- 用户级CLI可以复用模型缓存，但不同Python环境的依赖不会自动共享；Docling仍需要自己的RapidOCR库，权重文件可共用
- 包安装不等于模型已经就绪；固定版本、初始化模型、校验哈希和模型路径后再运行。RapidOCR还需显式安装ONNX Runtime
- 预热后平均时间、首次启动时间和网页等待时间不是同一个指标；并行适合减少等待，顺序适合做单机性能比较
- RSS是观察到的进程内存，不等于净物理内存或GPU完整占用；本轮Rapid峰值出现在极窄竖排，不代表普通图常态
- 输入、参考、运行目录、报告目录都需要明确版本；仅给父进程改目录不能保证worker也换目录
- Ctrl-C时必须清理独立进程组并保存中断状态，不然“停止”后模型可能继续运行
- 轻量回归负责逻辑边界，少量真实输入验证安装/进程链路；不是每次文档或评分修复都要重跑全部模型

## 证据与尚未回答的问题

本轮参考是上游人工标注加AI目视复核，未独立双人裁决；60区域来自47父页、2322非空白字素，置信区间较宽。不能把这些数字外推所有中文、客户真实分布、票据字段或复杂文档

整页文字、阅读顺序、表格TEDS、公式等仍需独立金标准和相应指标。要进一步做客户技术选型，优先固定客户真实业务小样本并校对答案，不继续无目的增加模型名单

实现与回归依据：[评价协议](ocr-evaluation-v3.md)、[六项修复记录](review-fixes.md)、tests目录。历史报告保留当时配置与口径，当前结论不覆盖旧证据
